# Design Review

画面の実装が、この repo の**明文化されたガイドライン**に沿っているかをレビューする。
正は Figma でも Storybook でもなく、**リポジトリ内の文書と `tools/design_lint.py`**。

引数として渡された対象: $ARGUMENTS

## 既存 `/code-review` との境界（重複しない）

| | `/code-review` | 本スキル |
|---|---|---|
| 見るもの | 正しさのバグ・重複・効率・簡素化 | **規約からの逸脱**（形・文言・トークン・アクセシビリティ・冗長） |
| 対象 | 全レイヤー（engine 含む） | **`app/src/main/java/com/magi/app/ui/**` のみ** |
| 根拠 | コードそのもの | **下の「根拠の優先順位」の文書** |

エンジン（`v6/`・`model/`）・重み・採否ロジックは**本スキルの対象外**。触れたくなったら指摘でなく `Q` で出す。

## 根拠の優先順位（衝突したらこの順で裁く）

1. **CLAUDE.md の決定記録（D3〜D8・E5）と HF77** — 覆さない。逸脱を見つけても**指摘にしない**（下の severity 規則）。
2. **`tools/design_lint.py`（P1〜P7）** — 機械検出できる領域はこれが正。目視で重ねて指摘しない。
3. **`docs/DESIGN.md`** — 原則・トークン参照（`MainActivity.MagiTheme` の色/タイポ/角丸 ＋ `MagiTokens.kt`）・禁止事項。
4. **`docs/operator_ux.md`** — 設計の5原則・**言い換え表（IT用語→ふつうの言葉）**。文言の正。
5. **`docs/screen_spec.md` / `docs/magi_design_system.md`** — 画面の挙動・実寸・部品。
6. **`docs/ux_test_checklist.md`（A〜N）** — WCAG / Nielsen / スマホ判読性のチェック項目。
7. **既存実装** — 現状把握と「変更を最小に保つ」制約であって、デザインの正ではない。

アクセシビリティ（コントラスト・タッチ域・色以外のチャネル）は順位に関係なく常に優先する。
この順で裁けない矛盾は推測で埋めず `Q` として出す。

## 手順

### Step 1. 対象の特定とスコープ判定

- 引数が空なら `git diff --stat` と `git diff` から UI 層の変更ファイルを対象にする。
- 対象が `ui/` の外（`v6/`・`model/`・`work/`）なら**そこで止める**。「対象外（/code-review の領域）」と述べて終える。
- Composable 名で指定された場合は `grep -n "fun <名前>(" app/src/main/java/com/magi/app/ui/` で位置を特定する。

### Step 2. 根拠の収集（**無ければ「対象外」と明示する。暗黙にスキップしない**）

対象の画面/カードについて、上の優先順位の文書から該当節を実際に読む。
- `docs/screen_spec.md` にその画面の節があるか（`grep -n "<画面名>" docs/screen_spec.md`）
- `docs/operator_ux.md` §2 の言い換え表に、その画面が出している語が載っていないか
- CLAUDE.md にその画面の変更履歴と**決定**が無いか（`grep -n "<画面名>\|<Composable名>" CLAUDE.md`）

根拠が1つも見つからないときは、**推測でレビューしない**。「この画面はガイドラインに記述が無いため対象外。
先に `docs/screen_spec.md` へ節を追加するか、`Q` として設計意図を確認してください」と述べる。

### Step 3. 機械検査を先に走らせる

```
python3 tools/design_lint.py
```
P5/P6/P7 は非ゼロ終了＝**必ず MUST**（コンパイルエラー・失敗色の残留・出荷される文字化け）。
P1〜P4 は baseline 監視なので、**対象ファイルの行が新たに増えていなければ指摘しない**。

### Step 4. 照合（観点）

この repo が実際に踏んで直してきた型。各行の括弧は根拠となる版。

**形が語るか**
- 説明文で操作を補っていないか。**貼り紙が要る時点で形が伝えられていない**（3.396.0）。
- 同じ操作は同じ形か。`›`＝押せる行、色を変える＝枠＋色見本、削除＝同じ形（3.397.0）。
- 押せる行と押せない行が同じ見た目で混ざっていないか（3.402.0）。
- **守れない約束をしていないか**。開けるのに拒否する、断言して直せない（3.405.0 / 3.401.0 / 3.364.0）。

**操作の返事**
- 押した結果が返るか。イベント＝Snackbar／状態＝上部バッジ・進捗行（3.399.0）。
- 失敗と成功が同じ見た目・同じ長さになっていないか（`messageIsError`・3.400.0）。
- 失敗パスが無言で終わっていないか（`logOp` に残るか・3.382.0）。

**入力**
- 事後の診断だけで通していないか。**入力時に止められるものは止める**（3.403.0）。
- 取消のボタンがあるか。アクションが取消の位置に置かれていないか（3.398.0）。

**文言**
- `docs/operator_ux.md` §2 の言い換え表に反していないか。
- 英字符号・内部語（`ws1`・`c3n`・`covU`・`V6`・`HARD`）を画面に出していないか（3.147.0 / 3.133.0 / 3.191.0）。
- 生の例外文・生の enum を出していないか（3.400.0 / 3.069.0）。

**トークン・アクセシビリティ**
- 色/角丸/余白が `MagiTheme`・`MagiTokens.kt` 由来か（生値の直書きは P2/P4 が見る）。
- コントラスト 4.5:1（大テキスト・UI部品は 3:1）。意味を**色だけ**で伝えていないか。
- タッチ域。対象端末は**幅390dp以上**（D4）。外観は**UD固定**（D8）。

**冗長**
- 同じ数字・同じ機能が別カードと重複していないか（3.286.0 / 3.195.0 / 3.194.0）。

### Step 5. severity（gist の分類＋この repo 固有の規則）

| | 付ける条件 |
|---|---|
| `MUST` | 実害があり、その根拠を**示せる**（アクセシビリティ欠落・誤操作の誘発・lint P5/P6/P7）。根拠に実害の内容を書く |
| `SHOULD` | 明文ルールからの逸脱。根拠に文書の該当行を引用する |
| `IMO` | 推奨・使い分けレベル |
| `nits` | 機能と無関係な軽微な揺れ |
| `Q` | 判断が要る・情報が足りない |

**この repo 固有の規則**
- **D3〜D8・E5 に反する提案は severity を付けず `Q` に落とす**（再提案禁止の決定）。
- **HF77 該当（重み・パラメータ・スコア）は severity を付けない**。「要・明示の数値指示」として出す。
- **「説明文を足す」提案は原則 `IMO` 以下**。まず形で解けないかを先に書く（3.396.0）。
- **根拠を示せないものは `MUST`/`SHOULD` にしない。** 迷ったら下位へ倒す。
- **実行して確かめられるものは確かめてから `MUST`**（`design_lint.py`・ホストJVM テスト。教訓#30）。

### Step 6. 出力

```
## 対象
<ファイル:行 / 画面名>・根拠にした文書の節

## 機械検査
design_lint.py: P5=0 P6=0 P7=0（P1-P4 は baseline 監視・新規増分なし）

## 指摘
- [MUST] <要約>
  根拠: <文書の引用 or 実害>
  該当: <file:line>
  直し方: <具体案>
- [SHOULD] ...
- [Q] ...

## 集計
MUST: N / SHOULD: N / IMO: N / nits: N / Q: N
判定: <MUST と SHOULD がともに 0 なら「ガイドライン準拠 OK」、それ以外は「要対応」>
```

## やってはいけないこと

- 根拠を示せない指摘に `MUST`/`SHOULD` を付ける。
- ガイドラインに記述の無い画面を、推測でレビューする（「対象外」と明示する）。
- 決定記録（D3〜D8・E5）を蒸し返す。
- lint が見る領域（P1〜P7）を目視で重複して指摘する。
- エンジン・重み・採否ロジックへ踏み込む（`/code-review` と HF77 の領域）。
- 指摘だけ出して**直した結果を確かめない**（`design_lint.py` は必ず再実行する）。
