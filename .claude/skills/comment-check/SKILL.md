# comment-check（追加コメントの点検）

> **IMPORTANT: 実装中に書いたコメントは、書いた本人には非自明に見える。記憶で判断せず、必ず抽出して1行ずつ見直す。**
> ルールを CLAUDE.md に置いても集計上は効かず、手順（抽出→1行ずつ判定）にして初めて減った、という
> 計測結果（Zenn, UZU テックブログ 2026-09-03）に基づく。このリポジトリでも直近29コミットの
> コメント比率は中央値 24.0%・4行以上の塊が中央値3個/コミットで、記事の「ルールなし」より多かった（3.497.1）。

対象: $ARGUMENTS（省略時は作業ツリーの未コミット差分）

## 手順（省略しない）

1. **抽出する**（判断の材料は記憶でなくこの出力だけ）
   ```bash
   python3 tools/comment_ratio.py            # 作業ツリー vs HEAD
   python3 tools/comment_ratio.py --range A..B   # PR 全体
   ```
   `file:line: 本文` の一覧と、比率・4行以上の塊の数が出る。
2. **1行ずつ判定する**。出力の全行を下の表に当て、`残す / 消す / 縮める / 移す` のどれかを付ける。
   まとめて「概ね妥当」と言わない。判定は次の形で書き出す:
   ```
   V6HotfixPasses.kt:412  // 旧: 部分窓も許していた…      移す → docs/history（3.495.0 の節に既にある）
   Program.cs:39          // Application.Start のラムダ…   縮める → 1行「引数名 _ は破棄でなく実引数（CS0029）」
   ```
3. **直す**。「移す」はその節が docs/history（または README の記録・commit message）に**既にあるか**を確認し、
   無ければ書いてから消す（情報を捨てない）。塊は原則2行以内へ。
4. **もう一度抽出して**、残った行数・比率・塊の数を before/after で commit message の本文に1行書く。
   例: `comment-check: 41→17 行, 11.7%→5.4%, 塊 2→0`

## 判定表

| 判定 | 該当するもの |
|---|---|
| **残す** | コードから復元できない「なぜ」: 値・順序・閾値の理由（例: 比較順は hard→weightedScore→total、重みは HF77 のユーザー指示）。落とし穴の警告（この順で呼ばないと壊れる・この API はこう振る舞う）。不変条件（state を書き換えない・スコアリング不変）。**言語跨ぎの対応義務**（Kotlin/C++/C# の同じ場所を一緒に変えろ）。1〜2行で足りる |
| **移す**（docs/history・README の記録・commit message へ） | 変更履歴（「旧: …」「以前は…だった」「3.4xx.0 で…」）。run ID・PR 番号・レビュー第N弾・実機報告の引用。検証の記述（「ホスト JVM で 588 テスト緑」）。試して否決した案の経緯 |
| **消す** | コードの直訳（「null なら早期 return」「i を進める」）。型や名前を繰り返すだけの KDoc/XML doc。`docs/business-logic.md` 等に既にある説明の複写。自分への実況（「ここで一旦…」） |
| **縮める** | 4行以上の塊。「なぜ」の1〜2行を残し、残りは移す/消す。塊を残すなら判定に理由を書く |

- **対象は差分で追加した行だけ**。既存コメントの一括掃除はしない（コメントの主張と実装を grep で照合するのが
  この repo の規律＝HF77。掃除は別タスクで、照合しながら行う）。
- 判定に迷う行は「移す」に倒す。docs/history は版数で引ける索引があるので、そこにあれば失われない。
- 記事の計測どおり、`(UZU-XXXX)` のような**正規表現で決まるものは減り、「旧実装は〜」の変更履歴は手順でも残りやすい**。
  変更履歴の行は特に意識して「移す」。
