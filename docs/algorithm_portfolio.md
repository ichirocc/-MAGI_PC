## 入口

探索・構築を起動するのは次の4種類だけ。UI・CSV・診断はアルゴリズム入口ではなく、結果を表示・保存・説明する。

| 入口 | 役割 | 実装 |
|---|---|---|
| 本最適化 | 初期解から広域探索して最良解を作る | `V6FinalPort.handleOptimize` → `V6NativeOptimizer.optimize` |
| 後処理 | 既存の良解を退化させずに制約別の残差を磨く | `V6HotfixPasses.runPostOptimization` |
| 初期解生成 | 希望・C1 を優先した下書きをゼロから組む | `V6FinalPort.handleSmartInitial` → `SmartInitialScheduler`（簡易版は `handleSimple` → `GreedyMirrorScheduler`） |
| 手動提案 | 利用者が確認して適用する一手を列挙する | `FixSuggester.suggest` |

`V6FinalPort.handleCheck` は評価のみで探索を起動しない＝入口ではない。
`LightMirrorOptimizer` は UI から参照ゼロ（`MirrorEngineTest` のみ使用）で、本番の入口ではない。

## 本最適化（広域探索）

| 層 | 方式 | 責務 |
|---|---|---|
| 基準 | V5 | 並列 SA。短予算時の安定した基準解。 |
| 破壊・修復 | ALNS | destroy/repair、Tabu、GLS、受理戦略（SA / GreatDeluge / Lam）を組み合わせる探索。 |
| 重点修復 | RSI / RSI+ | 最も重い違反族へ探索資源を寄せる。RSI+ は seed → 仮説 → refine を連結。 |
| 適応ポートフォリオ | PORTFOLIO | 複数仮説を epoch ごとに再配属し、エリートと多様性を保持。 |
| 自動選択 | AUTO | 予算に応じて上記を選ぶ（`V6FinalPort.optimizationPlan`）。 |

評価の真実は `Evaluator` / `DeltaEvaluator` と `UnifiedViolationChecker` の共通重み。
各探索器が独自の採否順を持たないよう、最終採否は `betterReport` に統一されている。

本最適化の終盤（`runPostOptimization` の**手前**）で `EliteIntegrationPolish` が走り、
蓄積したエリート盤面を Path Relinking / Fusion で統合する。採否は checker ＋ `betterReport` ＋
`exactPinRegression` の3段。

### 適応ポートフォリオの時間配分（実測値）

役割ごとの epoch 長（量子）は ALNS / RSI が 5〜8 秒、RSI+ が 35〜45 秒。役割の巡回は epoch の
**回数**で均等なので、実際に消費する**秒**は 7〜9 倍開く。この配分は診断ログの
`AdaptivePortfolio` 行に「役割別worker秒」として出る（`roleMillis`、読み取り専用）。

実測（real_state / 300秒 / 8ワーカー＝計 2,396 worker秒）:

| 役割 | 実消費 |
|---|---|
| MAX_DISTANCE_RSI_PLUS | 664s (27%) |
| HARD_DEBT_RSI_PLUS | 582s (24%) |
| BASELINE_REFINE | 424s (17%) |
| ELITE_RELINK | 174s (7%) |
| LARGE_DESTROY_ALNS | 154s (6%) |
| DAY_BLOCK_ALNS | 151s (6%) |
| PERSONAL_RSI | 138s (5%) |
| HARD_FAMILY_RSI | 105s (4%) |

**この偏りは是正しない。** 長い量子が付いている RSI+ 系の役割は、名前が示す族を狙うだけでなく
seed → 仮説 → refine → 研磨の一連を回すため、秒あたりの仕事量が短量子の役割より多い。
配分を均そうとすると epoch 境界の固定費（摂動・フル検査・距離計算）を払う回数が増えるだけになる
（根拠は下の「実測で否決した提案」）。

## 後処理（`runPostOptimization`）

前段（1回だけ） → 巡回ループ（最大4巡・1手も採用が無ければ打ち切り） → 後段（1回だけ）の3部構成。
全パスが keep-best のため、どこで打ち切っても入力より悪くならない。

## 手動提案は自動探索から分離

`FixSuggester` は利用者へ説明可能な単発手（変更、交換、連鎖、日内再最適化）を返す。
自動最適化の探索演算子と見た目が似ていても、利用者の確認を前提とするため後処理ポートフォリオへ混ぜない。

### `StagnationEscapeController` の決定表（ON のときだけ効く）

制御器が変えるのは**次の役割の選択だけ**。候補の採否、全体最良、終了判定はどれも変更しない。
すべて従来どおり checker の `betterReport` が決める。

下の表は上から順に評価する。**この表は `StagnationEscapeController` の全分岐を尽くしている**
（3.308.1 で実コードと1行ずつ突合し、欠けていた「改善したとき」「どの残差にも当たらないとき」の
2行を追加した）。

| 観測 | 次の手 |
|---|---|
| W0 | 常に `BASELINE_REFINE`。安全な基準軌道を離れない。 |
| 初期 epoch | W1/2/3/5/6/7 が Day ALNS / HARD RSI / HARD debt RSI+ / Large destroy / Personal RSI / Max-distance RSI+ を1本ずつ担当する。 |
| **改善した（停滞深さ 0）かつ peer と衝突していない** | **役割を変えず、強度だけ基準へ戻す。**うまくいっている手を取り上げない。 |
| peer との距離が 2 セル以下 | `MAX_DISTANCE_RSI_PLUS` と `LARGE_DESTROY_ALNS` を交互に選び、同じ吸引域の再試行を避ける。改善していても優先する（同じ盤面に落ちた2ワーカーは独立な情報を出していないため）。 |
| W4 の初回停滞（かつ異なる peer がある） | `ELITE_RELINK`。 |
| HARD 残差 | 主手は `HARD_FAMILY_RSI`。深い段では `HARD_DEBT_RSI_PLUS`。 |
| 時系列・日別残差（c1 / c3 / c3m / c3mn / c3n / c41 / c42 / c41s / c42s / covO） | 主手は `DAY_BLOCK_ALNS`。 |
| 個人回数・平準化残差（low / high / c2 / apt / fair / weekly） | 主手は `PERSONAL_RSI`。 |
| **どの残差にも当たらない** | **主手も深い段も `LARGE_DESTROY_ALNS`。** |
| 異なる peer がある | 再結合の段が `ELITE_RELINK` になる（いなければ `LARGE_DESTROY_ALNS`）。 |
| 候補がすべて現在の役割と同じ | 役割を変えない（`firstDifferent` のフォールバック）。 |

残差の判定は族ごとの `breakdown > 0`。HARD は `report.hard > 0`。同じ epoch で複数の残差が立つ
ことは普通にあり、主手の優先順位は HARD → 時系列 → 個人回数の順。

停滞深さは**自己エリートが改善しなかった連続 epoch 数**であり、役割を替えてもリセットしない。
改善したときだけ深さと強度を戻す。通常の停滞では
`制約別の主手 → 再結合 → 多様化 → 深い破壊` の4段を決定的に巡回する。

### 役割が変わった直後の量子（両経路が共有する契約）

epoch 長（量子）は「直前の epoch が改善したか」で 5→8 秒 / 35→45 秒に伸びる。ただし
**役割が変わった直後はこの延長を引き継がない**。新しい役割はまだ何も証明していないのに、
前の役割が稼いだ改善で長い量子を受け取る根拠が無いため。判定は
`AdaptiveHypothesisEpochPolicy.carriesImprovingQuantum` の1か所にあり、既定経路と制御器経路の
両方がそれを呼ぶ（3.308.0。それ以前は制御器経路だけがこの契約から外れていた）。

### 適応ポートフォリオの役割別秒予算（3.307.0）

**提案**: 300秒 × 8ワーカー＝2,400 worker秒を役割ごとに固定配分する（DayBlock 605s、
Elite relink 575s、Large destroy 320s、Max distance 295s、Personal 200s、Baseline 335s、
HARD 系 35s ずつ）。ワーカーごとの時間割も指定。動機は「DayBlock と Personal が 5 秒量子で
飢えている」。

**前提は実測で確認できた**（上表）。飢餓は実在し、提案が述べるより大きい。

**それでも否決**。固定表ではなく原因側（① 各ワーカーの HF63 が「残る HARD は充足困難」と学習済み
なら HARD 狙いの役割を配らない ② 代わりに実消費**秒**が最少の役割を選ぶ）を直す版を実装し、
3データセット × 3シード × ON/OFF ＝ 18 実行で A/B した結果:

- 予算は狙いどおり動いた（HARD_DEBT 24%→12%、DAY_BLOCK 6%→10%、PERSONAL 5%→8%、
  HARD 役の振替 24 回）。
- 品質は **9 ペア中 OFF が 6 勝・ON が 3 勝**、weighted 合計は OFF が 0.43% 良い。
  real は 3/3 で OFF が勝ち、c1 は user で 3/3 ON が悪化。ON を支持する結果はどこにも無い。
- 原因: ON 実行では archive が 25 → 43、つまり epoch が 18 回増えた。短い epoch は
  境界の固定費（摂動・フル検査・距離計算）をその回数だけ余分に払う。長い量子を短い量子へ
  置き換えることは、仕事を再配分するのではなく固定費を増やす。

提案の固定表は同じ方向へさらに強く振る（DayBlock を 6% → 25%、実験した版は 10%）ため、
方向が誤りであれば悪化幅は大きくなる（これは実測ではなく上記からの推論）。

**運用ルール 1〜3 についても採らない**: ルール 1（35 秒で HARD が下がらなければ打ち切る）は
HF63 の学習と ForbiddenDiag の構造壁判定が既に担っており、固定時間の閾値は別データで
まだ下がる HARD を切ってしまう。ルール 2（MAX_DISTANCE を連続させない）は
`StagnationEscapeController` の DISTINCT_PEER 圧力と同趣旨で、既に既定 OFF で温存済み。
ルール 3（終盤 60 秒は研磨優先）は後処理の予約枠が現状でも使い切られていない（3.102.0）。

## 追加・削除の規律

1. まず既存の責務表に置き場所を決める。新しい入口は増やさない。
2. 自動経路から外す前に、到達性・代表盤面・既存テストで代替手を確認する。**寄与ゼロの実測**を根拠にする。
3. 有益さは実測で示す。安全（keep-best で退化しない）と有益は別物で、利得が一貫しないものは
   撤去でも既定 ON でもなく「実装済みだが既定 OFF」へ置く。
4. 目的関数、重み、業務データはこの整理では変更しない（HF77）。
5. 各候補は希望固定 → 担当可否 → 厳密ピン → 正式評価（checker）の順に守る。
6. この台帳に書くのは実装済みの事実だけ。構想は「未実施の提案」節に置く。
7. 実装して測って有益さを示せなかったものは、コードを残さず「実測で否決した提案」へ根拠つきで
   記録する。前提が正しくても結論が正しいとは限らないので、**前提の確認と採否は分けて書く**。
