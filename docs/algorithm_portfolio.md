## 入口

探索・構築を起動するのは次の4種類だけ。UI・CSV・診断はアルゴリズム入口ではなく、結果を表示・保存・説明する。

| 入口 | 役割 | 実装 |
|---|---|---|
| 本最適化 | 初期解から広域探索して最良解を作る | `V6FinalPort.handleOptimize` → `V6NativeOptimizer.optimize` |
| 後処理 | 既存の良解を退化させずに制約別の残差を磨く | `V6HotfixPasses.runPostOptimization` |
| 初期解生成 | 希望・C1 を優先した下書きをゼロから組む | `V6FinalPort.handleSmartInitial` → `SmartInitialScheduler`（簡易版は `handleSimple` → `GreedyMirrorScheduler`） |
| 手動提案 | 利用者が確認して適用する一手を列挙する | `FixSuggester.suggest` |

`V6FinalPort.handleCheck` は評価のみで探索を起動しない＝入口ではない。
`LightMirrorOptimizer` は UI から参照ゼロ（`MirrorEngineTest` のみ使用）で、本番の入口ではない。

## 本最適化（広域探索）

| 層 | 方式 | 責務 |
|---|---|---|
| 基準 | V5 | 並列 SA。短予算時の安定した基準解。 |
| 破壊・修復 | ALNS | destroy/repair、Tabu、GLS、受理戦略（SA / GreatDeluge / Lam）を組み合わせる探索。 |
| 重点修復 | RSI / RSI+ | 最も重い違反族へ探索資源を寄せる。RSI+ は seed → 仮説 → refine を連結。 |
| 適応ポートフォリオ | PORTFOLIO | 複数仮説を epoch ごとに再配属し、エリートと多様性を保持。 |
| 自動選択 | AUTO | 予算に応じて上記を選ぶ（`V6FinalPort.optimizationPlan`）。 |

評価の真実は `Evaluator` / `DeltaEvaluator` と `UnifiedViolationChecker` の共通重み。
各探索器が独自の採否順を持たないよう、最終採否は `betterReport` に統一されている。

**近傍の共通規約**：探索も研磨も**実現可能な希望が入ったセル（`Problem.wishLocked`）を触らない**。
入口の `hf67HardRepair` と `Problem.initialAssignment` が実現可能な希望を先に盤面へ入れるので、
触らなければ正しいまま残る。3.334.0 まで SA/LAHC の近傍だけがこの規約から外れており、
**手の 35〜36% が採点でほぼ必ず却下される手**に費やされていた（pref は hard＝差分が 1e9 単位になる）。
複数セルを同時に変える手（`opBlockFill`／`opLns`）は、固定セルを飛ばして続けるのでなく
**手ごと見送る**（3.341.0）。途中が抜けた窓は「窓を埋める」という手の意図を果たさないまま
多数のセルを壊すだけだった。実データでは `opBlockFill` の 87〜100% が部分適用になっていた。

本最適化の終盤（`runPostOptimization` の**手前**）で `EliteIntegrationPolish` が走り、
蓄積したエリート盤面を Path Relinking / Fusion で統合する。採否は checker ＋ `betterReport` ＋
`exactPinRegression` の3段。

### 適応ポートフォリオの時間配分（実測値）

役割ごとの epoch 長（量子）は ALNS / RSI が 5〜8 秒、RSI+ が 35〜45 秒。役割の巡回は epoch の
**回数**で均等なので、実際に消費する**秒**は 7〜9 倍開く。この配分は診断ログの
`AdaptivePortfolio` 行に「役割別worker秒」として出る（`roleMillis`、読み取り専用）。

実測（real_state / 300秒 / 8ワーカー＝計 2,396 worker秒）:

| 役割 | 実消費 |
|---|---|
| MAX_DISTANCE_RSI_PLUS | 664s (27%) |
| HARD_DEBT_RSI_PLUS | 582s (24%) |
| BASELINE_REFINE | 424s (17%) |
| ELITE_RELINK | 174s (7%) |
| LARGE_DESTROY_ALNS | 154s (6%) |
| DAY_BLOCK_ALNS | 151s (6%) |
| PERSONAL_RSI | 138s (5%) |
| HARD_FAMILY_RSI | 105s (4%) |

**この偏りは是正しない。** 長い量子が付いている RSI+ 系の役割は、名前が示す族を狙うだけでなく
seed → 仮説 → refine → 研磨の一連を回すため、秒あたりの仕事量が短量子の役割より多い。
配分を均そうとすると epoch 境界の固定費（摂動・フル検査・距離計算）を払う回数が増えるだけになる
（根拠は下の「実測で否決した提案」）。

## 手動提案は自動探索から分離

`FixSuggester` は利用者へ説明可能な単発手（変更、交換、連鎖、日内再最適化）を返す。
自動最適化の探索演算子と見た目が似ていても、利用者の確認を前提とするため後処理ポートフォリオへ混ぜない。

### `StagnationEscapeController` の決定表（ON のときだけ効く）

制御器が変えるのは**次の役割の選択だけ**。候補の採否、全体最良、終了判定はどれも変更しない。
すべて従来どおり checker の `betterReport` が決める。

下の表は上から順に評価する。**この表は `StagnationEscapeController` の全分岐を尽くしている**
（3.308.1 で実コードと1行ずつ突合し、欠けていた「改善したとき」「どの残差にも当たらないとき」の
2行を追加した）。

| 観測 | 次の手 |
|---|---|
| W0 | 常に `BASELINE_REFINE`。安全な基準軌道を離れない。 |
| 初期 epoch | W1/2/3/5/6/7 が Day ALNS / HARD RSI / HARD debt RSI+ / Large destroy / Personal RSI / Max-distance RSI+ を1本ずつ担当する。 |
| **改善した（停滞深さ 0）かつ peer と衝突していない** | **役割を変えず、強度だけ基準へ戻す。**うまくいっている手を取り上げない。 |
| peer との距離が 2 セル以下 | `MAX_DISTANCE_RSI_PLUS` と `LARGE_DESTROY_ALNS` を交互に選び、同じ吸引域の再試行を避ける。改善していても優先する（同じ盤面に落ちた2ワーカーは独立な情報を出していないため）。 |
| W4 の初回停滞（かつ異なる peer がある） | `ELITE_RELINK`。 |
| HARD 残差 | 主手は `HARD_FAMILY_RSI`。深い段では `HARD_DEBT_RSI_PLUS`。 |
| 時系列・日別残差（c1 / c3 / c3m / c3mn / c3n / c41 / c42 / c41s / c42s / covO） | 主手は `DAY_BLOCK_ALNS`。 |
| 個人回数・平準化残差（low / high / c2 / apt / fair / weekly） | 主手は `PERSONAL_RSI`。**ただし役割の内部 focus は apt → high → low → fair の順で、c2 と weekly は選べず `total` へ落ちる**（`adaptiveEpochStart`。3.308.2 の敵対トレースで判明した設計と実装の差。focus 連鎖を広げると探索経路が変わるため、A/B で示せるまで実装は変えない）。 |
| **どの残差にも当たらない** | **主手も深い段も `LARGE_DESTROY_ALNS`。** |
| 異なる peer がある | 再結合の段が `ELITE_RELINK` になる（いなければ `LARGE_DESTROY_ALNS`）。 |
| 候補がすべて現在の役割と同じ | 役割を変えない（`firstDifferent` のフォールバック）。 |

残差の判定は族ごとの `breakdown > 0`。HARD は `report.hard > 0`。同じ epoch で複数の残差が立つ
ことは普通にあり、主手の優先順位は HARD → 時系列 → 個人回数の順。

停滞深さは**自己エリートが改善しなかった連続 epoch 数**であり、役割を替えてもリセットしない。
改善したときだけ深さと強度を戻す。通常の停滞では次の4段を決定的に巡回する
（`(深さ-1) and 3` で選ぶ。各段の候補が現在の役割と同じなら次の候補へ送る）。

1. **制約別の主手** — 上表の残差から選ぶ（HARD / 時系列 / 個人回数 / 該当なし）。
2. **再結合** — `ELITE_RELINK`（異なる peer がいなければ `LARGE_DESTROY_ALNS`）。
3. **多様化** — `MAX_DISTANCE_RSI_PLUS`。
4. **深い破壊** — HARD が残っていれば `HARD_DEBT_RSI_PLUS`、それ以外は `LARGE_DESTROY_ALNS`。

深さが上がるほど `intensityFor` の強度も上がる（2エポック失敗ごとに +1、上限 +3）。

### 役割が変わった直後の量子（両経路が共有する契約）

epoch 長（量子）は「直前の epoch が改善したか」で 5→8 秒 / 35→45 秒に伸びる。ただし
**役割が変わった直後はこの延長を引き継がない**。新しい役割はまだ何も証明していないのに、
前の役割が稼いだ改善で長い量子を受け取る根拠が無いため。判定は
`AdaptiveHypothesisEpochPolicy.carriesImprovingQuantum` の1か所にあり、既定経路と制御器経路の
両方がそれを呼ぶ（3.308.0。それ以前は制御器経路だけがこの契約から外れていた）。

## 実測で否決した提案（再提案しない）

実装して測った結果、有益さを示せなかったもの。コードは残していない。同じ提案が再び出たときは
まずここを読む。

### 後処理研磨で Range(個人回数)を巡回クラスタの先頭へ移す（3.364.0 の A/B で否決）

**提案（敵対検証ケース6）**: 巡回クラスタは CyclicSwap→C1×5→C3×4→**Range**→… の順で、最重ソフト
（low=90/high=45）の Range が4番目。重み降順なら Range を先頭にすべき、という untested な reorder 仮説。

**host-JVM で `runPostOptimization`（固定seed）を Range先頭 vs 現順序で A/B（3データセット）**:

| データ | 種別 | 現順序 weighted | Range先頭 weighted | 判定 |
|---|---|---|---|---|
| golden | fixture | 2653 | **2530（−4.6%）** | Range先頭が改善（low 7→6・covO 3→2） |
| sample_v6 | fixture | 73783 | 73757（≈同値） | 中立（low 2→1 と c1 6→11 の構成入替で相殺） |
| **real3（実運用 2026-08）** | **実データ** | 33347/33318 | **完全一致** | **効果ゼロ**（cluster fixpoint が順序不変） |

**否決の理由**: 目的関数(weighted)では 3/3 で ≤（never worse）だが、**唯一の改善は golden（合成 fixture）のみ**で、
**実運用データ(real3)には利益ゼロ・sample_v6 は中立の構成入替**。測定済み隣接（3.254.0 temporalFlow<wideBeam・
3.300.0 BlockSwap は Range 後 Apt/Fair 前）を尊重した現順序を、fixture 限定の利得のために書き換えない。
**実データが tie を破って不採用を確定**（keep-best のため安全＝退化はしないが、有益でもない）。
順序自体は「安全（keep-best で退化不能）・実測隣接を尊重・3データセットで reorder に実利益なし」で正しい。

### 早期終了で余った予算を soft 研磨へ回す（3.341.1 の検証で否決）

**提案**: c3n の構造壁が証明されたあと、残り予算のうち 10〜25 秒を soft 研磨に使う。

**前提が実データで成立しなかった**（120秒・workers=4・実データ3件）。

| | 実測時間 | HARD 内訳 | 停滞監視 |
|---|---|---|---|
| golden | **55s / 120s** | すべて 0 | plateau（HARD下限到達）で発火 |
| real | 120s（全部使用） | c3n=1・covU=3 | 発火なし（実効閾値は通常=長108s） |
| user | 120s（全部使用） | c3n=1・covU=3 | 発火なし |

c3n が残る real/user では **ForbiddenDiag が構造壁と証明しておらず、そもそも時間が余らない**。
時間が余るのは **hard=0 に到達したとき**（golden で予算の54%）で、提案が想定した条件とは別物だった。

**その余りを使う穏当版（`ExtraRefine` の `stagnationFired` スキップを外し、予約枠 8〜25 秒だけ追う）を
5回ずつ測って否決**。事前に固定した基準「5回中4回以上が現行の中央値より良い」に対し **2/5**。

| golden 120s ×5 | 時間中央 | weighted 中央 | 平均 |
|---|---|---|---|
| 現行 | 51s | 2319 | 2362 |
| ＋追加精製 | 68s | 2393 | 2356 |
| 早期終了を撤去 | 119s | 2238 | 2265 |

**早期終了そのものの撤去**は中央 −3.5%・平均 −4.1% だが **U検定 p≈0.075 で有意でなく**（分布の幅が
326 もあり5サンプルでは示せない）、時間は 2.3 倍。これは品質と電池・待ち時間の交換であって
アルゴリズムの改善ではない＝**業務判断**（3.281.0 は実機ログで48秒の節約を成果として記録している）。
ここで記録しておくのは、「予算120秒を指定したユーザーに51秒で返している」という事実と、
その差が測った範囲では有意でなかったこと。

### C1 の「証明つき」頭打ち診断（C1FocusProof）を作る（3.323.0 の検証で否決）

**提案**: 窓ごとに `C1CandidateSearch`（候補探索）と `C1FocusProof`（FEASIBLE / INFEASIBLE_PROVEN /
UNKNOWN_BUDGET）を分け、「この窓はどう並べ替えても直せない」を厳密に証明して利用者へ出す。

**否決の理由（実測）**: `solveWindow` が `exhaustive=true`（＝node 予算内で全探索を完了＝証明成立）に
到達した窓は、**3 データセット・全 217 窓で 0 件**だった（patch も 0 件）。

| データ | 残 c1 窓 | 証明到達 | 予算切れ | 所要 |
|---|---|---|---|---|
| golden | 104 | 0 | 104 | 267ms |
| real | 59 | 0 | 59 | 65ms |
| user | 54 | 0 | 54 | 0ms（即 bail） |

原因は関与職員の基礎集合が平均 8.9〜9.8 人で上限 6 を先に超えること（上限を上げる案は下記のとおり別途否決済み）。
このまま作れば**常に UNKNOWN_BUDGET を返す＝何も言わない診断**になる。代わりに 3.323.0 では、証明ではなく

### C1 厳密窓修復の関与職員集合を選抜制にする（3.315.0 の検証で否決）

**提案**: `solveWindow` の関与職員集合 `mSet` は「スパン内でそのシフトを持つ職員」を**上限なし**で積むため
`maxInvolvedStaff` を超えて即諦める。焦点に近い順・c1 寄与順などで選抜すれば探索が実際に走る。

**否決の理由（実測）**: 一番根拠のある選抜基準は「焦点の不足窓内でそのシフトを持つ職員だけ」だが、
実データでは**絞ってもほとんど減らない**（窓は 5〜15 日幅で、休は 10 人中ほぼ全員が期間内のどこかで持つ）。

| データ | 不足窓内で持つ他職員 | 選抜なしで cap(6) に収まる窓 |
|---|---|---|
| real | 5人:6 6人:27 7人:20 8人:10 9人:15 | 6 / 78 |
| user | 5人:2 6人:3 7人:3 8人:16 9人:40 | 2 / 64 |
| golden | 5人:3 6人:28 7人:9 9人:75 | 3 / 115 |

つまり**どう選んでも恣意的**で、根拠のある基準が作れない。そして cap=10（=職員数＝bail ゼロ）で母数を
作って却下理由を測ったところ、**patch は出るが採用は 0・却下は全件がピン破りか c3n 増**と判明した。
ボトルネックは集合サイズではなく**探索の目的関数**（joint c1 しか見ていない）で、そちらを直したのが
3.315.0（厳密ピンと c3n を探索側にも入れる＝上の責務表 6 行目）。

### C1 厳密窓修復の関与職員上限を上げる（3.314.0 の検証で否決）

**背景**: `C1RepairAnalysis.solveWindow` は関与職員集合 M を「焦点職員 ∪ スパン内でそのシフトを持つ
職員（**上限なし**）」で作り、そのあとで余力職員を `maxInvolvedStaff`(=6) まで足す。実データでは
**基礎集合の時点で平均 8.9〜9.8 人**あり、`if (mSet.size > maxInvolvedStaff) return`（探索せず
`exhaustive=false` で戻る）に**ほぼ毎回当たる**:

| データ | c1 窓 | cap 即 bail | 探索到達 |
|---|---|---|---|
| real | 78 | 76 | 2 |
| user | 64 | 63 | 1 |
| golden | 115 | 112 | 3 |

つまり `applyC1ExactWindowRepair` は**この実データの c1 窓の約 97% で即座に諦めている**。
「では上限を上げれば厳密探索が効くのでは」という自然な提案を、上限 6→10（=職員数 S）で測った。

| データ | cap=6（現行）中央値 | cap=10 中央値 | weighted 6 → 10 |
|---|---|---|---|
| real | 20,982ms | **59,171ms** | 49231 → 49334（悪化） |
| user | 35,002ms | **82,491ms** | 33167 → 33167（同値） |
| golden | 24,543ms | **63,065ms** | 2469 → 2469（同値） |

**2.4〜2.8 倍遅くなって品質は 2/3 で同値・1/3 で悪化**（real の差は JointLNS の壁時計予算由来の
ばらつき帯＝3.279.1 の既知事項の範囲）。cap=6 は事故ではなく**効いている費用ガード**で、
探索に到達しないこと自体は品質を損ねていない。上限を触るなら、まず「基礎集合を無制限に積む」側の
設計から見直す必要がある（上限だけ上げても分枝限定が爆発するだけ）。

**副産物**: 3.314.0 の M-05（同群限定 → canDo 全体への候補拡張）は、この bail のため
**3データセットとも一度も実行されない**（拡張ループの前で戻るので、旧実装と関与職員集合が完全に一致
することを実測で確認）。一方 M-05 のもう半分＝**「cap で切り捨てたら `exhaustive` を名乗らない」**は、
探索に到達した窓の **2/2・1/1・3/3 すべてで `truncated` が立つ**＝旧実装ならそこで偽の
「証明済み壁」を出しえた地点で確実に効いている。**候補拡張は休眠・偽の壁の防止は稼働中**。

### PERSONAL_RSI の focus を重み最大の族にする（3.310.1）

**提案の前提は実測で正しかった**。`adaptiveEpochStart` の `PERSONAL_RSI` は
`apt → high → low → fair → total` の**固定順**で focus を選ぶが、重みは
**low=90 > high=45 > apt=fair=weekly=c2=1** ＝**一番軽い apt を最初に見ている**。実測（real/user、
PORTFOLIO 90秒×8ワーカー）で **20回の呼び出しすべてが `apt` を選び、重み最大の個人族は
20回すべて `low`(18)/`high`(2)。一致 0/20**。

そこで「重み×件数が最大の個人回数族を選ぶ」変種を作り、**3データセット × 5シード × 同一シードの
対比（15ペア）**で A/B した。判定基準は測る前に固定（B が weighted で 11/15 以上勝つこと）。

| データ | A 平均 | B 平均 | 差 |
|---|---|---|---|
| golden | 2269 | 2309 | B が 40 悪い |
| real | 32791 | 32710 | B が 81 良い |
| user | 32708 | 32806 | B が 99 悪い |

**結果は B が 6勝8敗1分**（符号検定 p≈0.79）。データセット間で符号も一貫しない。golden は5ランのうち
4ランで `PERSONAL_RSI` 呼出が 0 ＝ほぼ純粋なノイズ対照になり、それでも幅 ±150 出る。観測差の大半は
この帯の中に収まる。

**機構自体は設計どおり動いた**（B は狙いどおり `low` を減らす。real の low 合計 15→11）。それでも
weighted に変換されない。理由は実装から説明がつく：focus が low でも apt でも
`rsiGenerateHypothesis` は同じ `destroyRepairStaff` へ流れ、そこの marginal cost
`staffCountPenaltyAt` は**元から low=90 / high=45 を織り込んでいる**。修復側は focus に関わらず
low/high を意識しており、focus が変えるのは「どの職員を壊すか」だけ。だから狙う族を替えても
結果がほとんど動かない。

**教訓**：「明らかに間違って見える選択順」でも、下流がその情報を別経路で既に持っていれば直しても効かない。
前提の確認（0/20）と効果の確認は別物。

### 適応ポートフォリオの役割別秒予算（3.307.0）

**提案**: 300秒 × 8ワーカー＝2,400 worker秒を役割ごとに固定配分する（DayBlock 605s、
Elite relink 575s、Large destroy 320s、Max distance 295s、Personal 200s、Baseline 335s、
HARD 系 35s ずつ）。ワーカーごとの時間割も指定。動機は「DayBlock と Personal が 5 秒量子で
飢えている」。

**前提は実測で確認できた**（上表）。飢餓は実在し、提案が述べるより大きい。

**それでも否決**。固定表ではなく原因側（① 各ワーカーの HF63 が「残る HARD は充足困難」と学習済み
なら HARD 狙いの役割を配らない ② 代わりに実消費**秒**が最少の役割を選ぶ）を直す版を実装し、
3データセット × 3シード × ON/OFF ＝ 18 実行で A/B した結果:

- 予算は狙いどおり動いた（HARD_DEBT 24%→12%、DAY_BLOCK 6%→10%、PERSONAL 5%→8%、
  HARD 役の振替 24 回）。
- 品質は **9 ペア中 OFF が 6 勝・ON が 3 勝**、weighted 合計は OFF が 0.43% 良い。
  real は 3/3 で OFF が勝ち、c1 は user で 3/3 ON が悪化。ON を支持する結果はどこにも無い。
- 原因: ON 実行では archive が 25 → 43、つまり epoch が 18 回増えた。短い epoch は
  境界の固定費（摂動・フル検査・距離計算）をその回数だけ余分に払う。長い量子を短い量子へ
  置き換えることは、仕事を再配分するのではなく固定費を増やす。

提案の固定表は同じ方向へさらに強く振る（DayBlock を 6% → 25%、実験した版は 10%）ため、
方向が誤りであれば悪化幅は大きくなる（これは実測ではなく上記からの推論）。

**運用ルール 1〜3 についても採らない**: ルール 1（35 秒で HARD が下がらなければ打ち切る）は
HF63 の学習と ForbiddenDiag の構造壁判定が既に担っており、固定時間の閾値は別データで
まだ下がる HARD を切ってしまう。ルール 2（MAX_DISTANCE を連続させない）は
`StagnationEscapeController` の DISTINCT_PEER 圧力と同趣旨で、既に既定 OFF で温存済み。
ルール 3（終盤 60 秒は研磨優先）は後処理の予約枠が現状でも使い切られていない（3.102.0）。

## 追加・削除の規律

1. まず既存の責務表に置き場所を決める。新しい入口は増やさない。
2. 自動経路から外す前に、到達性・代表盤面・既存テストで代替手を確認する。**寄与ゼロの実測**を根拠にする。
3. 有益さは実測で示す。安全（keep-best で退化しない）と有益は別物で、利得が一貫しないものは
   撤去でも既定 ON でもなく「実装済みだが既定 OFF」へ置く。
4. 目的関数、重み、業務データはこの整理では変更しない（HF77）。
5. 各候補は希望固定 → 担当可否 → 厳密ピン → 正式評価（checker）の順に守る。
6. この台帳に書くのは実装済みの事実だけ。構想は「未実施の提案」節に置く。
7. 実装して測って有益さを示せなかったものは、コードを残さず「実測で否決した提案」へ根拠つきで
   記録する。前提が正しくても結論が正しいとは限らないので、**前提の確認と採否は分けて書く**。
