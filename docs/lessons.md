**要約**：作る前に前提を測ると無駄が消え、検証の穴（UI 層はホストでコンパイルできない・断定は観測を超えやすい）が事故の大半を生む。

このファイルは**追記でなく更新**する。新しい教訓が出たら該当行を書き換える／表に1行足す。
同じ趣旨の行が増えたら統合する。日付でなく「何をやめて何を続けるか」を残す。

## 2. 作る前にやめた判断（同じ提案が来たらここを読む）

- **C1 の証明つき頭打ち診断（`C1FocusProof`）**：厳密窓探索が「探索し尽くした」に到達した窓は
  3データセット・全217窓で **0件**。作れば常に UNKNOWN_BUDGET を返す＝何も言わない診断になる（3.323.0）。
- **関与職員上限の引き上げ・選抜制**：2.4〜2.8倍遅く品質は同値か悪化／絞っても母数がほとんど減らない（3.314.0/3.315.0）。

判断の型：**実装より先に「その機能が発火する条件が実データで成立するか」を測る**。
成立しないなら作らない。3.290.0 の「候補4件で採用0の不活性パス」を出したのが元の失敗。
否決はコードを残さず、根拠つきで `docs/algorithm_portfolio.md` の「実測で否決した提案」へ書く。

## 3. 測り方

- **1回の計測で A/B を判定しない。** 3回以上回して分布で見る。JointLNS は壁時計予算で動くので
  run 間に幅が出る（real の既知帯 49213〜49232）。同一 JVM 内の実行順でも変わる。
- **`weighted` を見る。`c1` 単体で判断しない。** 目的関数は hard → weightedScore → total の順で、
  c1(15) 2件を手放して low(90) 5件を消す取引は正しい改善。族の件数だけ見ると悪化に見える。
- **前提の確認と効果の確認は別物。** 「focus が一度も選ばれていない（0/20）」が鮮やかに確認できても、
  下流が同じ情報を別経路で持っていれば直しても効かない（3.310.1 で実測）。
- **反実仮想は出荷せずに測れる。** データを書き換えず、緩めた版で研磨だけ回して差を見る。

## 4. この環境の検証手段と穴

| 層 | 検証できるか | 手段 |
|---|---|---|
| v6 エンジン・model | **できる** | ホスト JVM で実コンパイル＋JUnit 実行（Gradle 同梱の `kotlin-compiler-embeddable`）。実データ3件で最終盤面の不変も確認 |
| C++ / JNI | **できる** | `tools/native/host_parity_bench.cpp` を g++ で実ビルド・実行（mismatch=0）。CI にも配線済み |
| UI（Compose）・ViewModel・WorkManager | **できない** | 括弧均衡・シンボルのスコープ逆引き・呼び出し側シグネチャの静的確認まで。**最終判定は CI**。実行の所有権・kill 復元のような並行性はエミュレータ/実機でしか確かめられない |

**穴はここ**：UI 層は静的チェックが通ってもコンパイルが通る保証がない（#1・#17 がその実例）。
括弧均衡とスコープ逆引きは**構造**しか見ない。**名前**（プロパティ・関数のシグネチャ）は別途モデル定義と
突き合わせる。
機械的な一括編集をしたら、**エンジン層は必ずコンパイルまで通してから次へ進む**（型の不整合・引数の重複は
コンパイラだけが見つける。3.326.0 は18関数への一括配線で「引数を二重に渡した」等を実際にコンパイルで捕まえた）。
CI を起動したら**結果を確認するまで次へ進まない**。「CI 待ち」と書いて別の作業を始めた結果、
失敗に気づくのが1ターン遅れた。

## 5. 受け取ったレビューの扱い
