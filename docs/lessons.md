# 教訓メモ

**要約**：作る前に前提を測ると無駄が消え、検証の穴（UI 層はホストでコンパイルできない・断定は観測を超えやすい）が事故の大半を生む。

このファイルは**追記でなく更新**する。新しい教訓が出たら該当行を書き換える／表に1行足す。
同じ趣旨の行が増えたら統合する。日付でなく「何をやめて何を続けるか」を残す。

最終更新：2026-07-30（3.321.0〜3.329.0 の作業から）

## 1. 修正した点 ↔ 機能した点（対で読む）

| # | 修正した点（やってしまったこと） | 機能した点（次も続けること） |
|---|---|---|
| 1 | **アンカー行の一致だけで挿入位置を決めた**。同じ誤りを2度踏んだ: (a)`val mappedDiag = ...` は `analyzeParallel` と `makeUi` の2箇所にあり最初の一致（別の関数）に入った（3.324.1） (b)複数行の呼び出し `val rBlockSwap = applyAdaptiveBlockSwapPolish(` の**次の行**へ挿入し、引数リストの途中に文が入った（3.326.0） | 挿入は**アンカーが「文の終わり」かを確かめてから**行う。同名行が複数あるファイルでは置換アンカーに関数境界を含める。編集後は**宣言行と使用行が同じ関数に属するか**を行番号から逆引きして検査する（括弧均衡は 0 でも通ってしまう） |
| 2 | **UI へ運ぶ値を、UI を作る関数より後で代入**した。`pushReport`（`makeUi` を呼ぶ唯一の経路）のあとに診断を代入し、その回の画面に出なかった（3.322.0→3.324.0） | 値の生産と消費の**順序を経路で確認する**（「makeUi を呼ぶのはどこか」を先に grep する） |
| 3 | **採用しなかった盤面の診断を保存**し、かつ**無効化する経路を作らなかった**。手編集後も古い観測が出続けた（3.322.0/3.323.0→3.324.0） | 再計算できない値は**どの入力に対する観測か**を持たせる。盤面の内容ハッシュで自己失効させる方式にした（変更サイトごとにフックを足すと必ず漏れる） |
| 4 | **件数の意味を強く書いた**。`pinBlocked` を「全パス横断・手の数」と書いたが、実際は9パスのみ・試行回数・最大4巡を重複排除なし（3.323.0→3.324.0） | 集計を出すときは**母集団と単位を先に確認**する。言えるのは「少なくとも N 回」までだった |
| 5 | **「0 なら緩めても何も変わらない」と断定**した。未計測のパスがあるので証明にならない（3.323.0→3.324.0） | 観測ベースの診断は**観測の範囲を超えない**。「構造的に不能」「すべて」「必ず」を使う前に、その主張を反証できる手が探索側に無いか確かめる |
| 6 | **緩め幅を決め打ち**して「1回ぶん緩めると通る」と書いた。実測では ±1 と ±3 の優劣がデータで逆転した（3.323.0→3.324.0） | 幅・閾値は**示さず判断材料だけ出す**。パラメータを動かすのは業務判断（HF77） |
| 7 | **件数の多数決で原因を分類**し、「スコア却下8・候補なし10」を「入れ替え相手が見つかりません」と案内した。実際は相手が居て禁止連続で落ちていた（3.322.0 初版） | 強い主張は**1件の反例で崩れる**。「候補なし」は候補が1件でも作れていたら名乗らない規則にした |
| 8 | **一つのパスの測定結果を全体へ一般化**した。「ピン破りが不採用の73〜100%」は Apt/Fair/C3系の話で、C1 自身は 0〜1件・主因は `low` だった（3.321.0→3.322.0） | 測った対象を**名前で限定して書く**。同じ設定を指していても、どちらのガードが先に発火するかでラベルが変わる |
| 9 | **原因の仮説を測る前に信じた**。exactWindow が諦める理由を「関与職員集合の選抜」と考えたが、測ったら別の場所（探索の目的関数）だった（3.314.0/3.315.0）。同型: レビューの「Block Swap が300秒を超える」を信じかけたが、測ると 18〜70ms で時間の問題ではなかった（3.327.0） | 疑った箇所を**先に計測して否定する**。仮説が外れたことを結論として記録する。**受け取った指摘の「重大度」も指摘の「事実」とは別に検証する**（食い違いは実在しても、理由が実在するとは限らない） |

| 11 | **観測がゼロだと機能もゼロだと決めつけかけた**。`attempts=0` のデータでも、反実仮想では緩和で weighted が改善する（緩和は下限割れの罰も外すので別経路が効く）（3.326.0） | 観測は**その観測点で見えたことだけ**を語る。「0 件だから効かない」は別の経路を否定していない |

## 2. 作る前にやめた判断（同じ提案が来たらここを読む）

- **C1 の証明つき頭打ち診断（`C1FocusProof`）**：厳密窓探索が「探索し尽くした」に到達した窓は
  3データセット・全217窓で **0件**。作れば常に UNKNOWN_BUDGET を返す＝何も言わない診断になる（3.323.0）。
- **関与職員上限の引き上げ・選抜制**：2.4〜2.8倍遅く品質は同値か悪化／絞っても母数がほとんど減らない（3.314.0/3.315.0）。

判断の型：**実装より先に「その機能が発火する条件が実データで成立するか」を測る**。
成立しないなら作らない。3.290.0 の「候補4件で採用0の不活性パス」を出したのが元の失敗。
否決はコードを残さず、根拠つきで `docs/algorithm_portfolio.md` の「実測で否決した提案」へ書く。

## 3. 測り方

- **1回の計測で A/B を判定しない。** 3回以上回して分布で見る。JointLNS は壁時計予算で動くので
  run 間に幅が出る（real の既知帯 49213〜49232）。同一 JVM 内の実行順でも変わる。
- **`weighted` を見る。`c1` 単体で判断しない。** 目的関数は hard → weightedScore → total の順で、
  c1(15) 2件を手放して low(90) 5件を消す取引は正しい改善。族の件数だけ見ると悪化に見える。
- **前提の確認と効果の確認は別物。** 「focus が一度も選ばれていない（0/20）」が鮮やかに確認できても、
  下流が同じ情報を別経路で持っていれば直しても効かない（3.310.1 で実測）。
- **反実仮想は出荷せずに測れる。** データを書き換えず、緩めた版で研磨だけ回して差を見る。

## 4. この環境の検証手段と穴

| 層 | 検証できるか | 手段 |
|---|---|---|
| v6 エンジン・model | **できる** | ホスト JVM で実コンパイル＋JUnit 実行（Gradle 同梱の `kotlin-compiler-embeddable`）。実データ3件で最終盤面の不変も確認 |
| C++ / JNI | **できる** | `tools/native/host_parity_bench.cpp` を g++ で実ビルド・実行（mismatch=0）。CI にも配線済み |
| UI（Compose）・ViewModel・WorkManager | **できない** | 括弧均衡・シンボルのスコープ逆引き・呼び出し側シグネチャの静的確認まで。**最終判定は CI**。実行の所有権・kill 復元のような並行性はエミュレータ/実機でしか確かめられない |

**穴はここ**：UI 層は静的チェックが通ってもコンパイルが通る保証がない（#1・#17 がその実例）。
括弧均衡とスコープ逆引きは**構造**しか見ない。**名前**（プロパティ・関数のシグネチャ）は別途モデル定義と
突き合わせる。
機械的な一括編集をしたら、**エンジン層は必ずコンパイルまで通してから次へ進む**（型の不整合・引数の重複は
コンパイラだけが見つける。3.326.0 は18関数への一括配線で「引数を二重に渡した」等を実際にコンパイルで捕まえた）。
CI を起動したら**結果を確認するまで次へ進まない**。「CI 待ち」と書いて別の作業を始めた結果、
失敗に気づくのが1ターン遅れた。

## 5. 受け取ったレビューの扱い

- **鵜呑みにせず全件コード照合する。** 今回は 5/5 が実在した（うち3件は自分が作った欠陥）。
  過去には事実誤認・既修正・対象コミットが古い、も混ざっていた。
- **提示されたファイルをそのまま適用しない。** 切断された作業コピー（MD5 一致の再送・末尾欠落・
  `TODO()` 混入・コンパイル不能な1文字）を実際に受け取っている。内容は「意図の記述」として読み、
  現行ファイルへ手で反映する。
- **成立しない指摘は根拠を示して不採用にする。** 「fallback elite の並びが hard→total」は
  3.287.0 の統一順どおりだった、など。
